The week in one sentence. Proposal cards

P1 | arxiv-2609.07492 | evidence tier: anecdote (single paper, abstract only) | proof: unproven

FPScan - floating-point anomaly detection

Claim. A comparator for this pipeline stands or falls on its tolerance policy, and constraint-based anomaly analysis is a better-founded starting point than a hand-picked epsilon (likely, 55-80%).

Why now. Dated 2026-09-09, one day before this heat, and it lands on a decision this repository has to make immediately: a ~1e-13 cross-environment drift is already on record here, and pandas' default tolerance has already once passed that drift silently.

What it displaces. Nothing yet - it is reading, not adoption. If it displaces anything later it would be the "pick an epsilon and see" approach.

Rollback. Free; nothing is integrated.

Strongest objection. No red team ran (phase 1). The obvious one stands unanswered: a constraint analyzer built for detecting anomalies inside a program may have nothing to say about comparing two program outputs, and the title is being asked to carry more than it may hold.

P2 | arxiv-2512.18088 | evidence tier: anecdote (single case study, abstract only) | proof: unproven

Flaky tests in quantum software - the Qiskit Terra case study

Claim. The dominant risk to this design is a false-positive rate that erodes trust in the report, and this is the closest published measurement of that rate in a numerically intensive, probabilistic codebase (likely, 55-80%).

Why now. Surfaced in this week's cs.SE feed. It matters now rather than later because the false-positive question should shape the design, not be discovered after the tool is in use.

What it displaces. Nothing. It is a prior on a number this project will otherwise guess.

Rollback. Free.

Strongest objection. Quantum simulation flakiness may be dominated by sampling noise that this pipeline, with fixed seeds, does not have - in which case its base rate transfers poorly and would be misleading if quoted.

P3 | gh-syrupy-v6.0.0 | evidence tier: vendor-claim (release notes) | proof: unproven

syrupy v6.0.0 - deterministic serialization, changed output format

Claim. The stored run format needs an explicit version in the manifest, because a change in how values are written invalidates every baseline without changing any value (very likely, 80-95%).

Why now. Released 2026-08-22. A mature snapshot library shipping precisely this in a major version is the failure mode made concrete rather than hypothesised.

What it displaces. The assumption that a baseline is self-describing. Concretely it adds one field to the run manifest, which is the smallest possible surface.

Rollback. Remove the field; nothing else depends on it.

Strongest objection. This is a lesson from a library this project will not use, applied to a format this project has not written yet. It could be premature structure for a thirty-row CSV.
